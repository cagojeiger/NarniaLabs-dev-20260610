## 2. 배경

Narnia Labs는 제조·설계 도메인에서 AI를 활용해 설계 시간을 줄이고 품질을 높이는 것을 목표로 하는 회사입니다. 현재 단계에서는 대규모 SaaS·K8s 플랫폼보다 단일 서버·로컬 중심의 빠른 실험과 데모가 중요한 시기입니다.

ML 모델 학습은 보통 워크플로우(DAG, Directed Acyclic Graph) 단위로 관리됩니다. 데이터 준비 → 학습 → 평가 → 배포 같은 노드들이 의존성을 가지고 실행되며, 각 노드는 로그와 메트릭을 남깁니다. 학습이 실패할 때 원인을 빠르게 짚고 액션을 제안하는 일이 매일 반복됩니다. 참고로 분석 대상이 되는 학습 잡은 일반적으로 PyTorch / TensorFlow / JAX 등 Python ML 프레임워크로 작성된 코드의 출력 로그·메트릭입니다.

이 과제는 그런 진단을 AI 에이전트가 자동으로 해주는 도구를 만드는 것입니다. 제조·설계 도메인 지식은 평가 대상이 아닙니다.

## 3. 과제

ML 학습 잡 실패 진단 에이전트를 설계하고 구현해 데모하세요.

### 3.1 필수 산출물

핵심 평가 대상은 (3) AI 에이전트입니다. (1)(2)는 (3)을 지지하는 컨텍스트로 얕은 PoC면 충분합니다. 시간 비중을 (3)에 가장 크게 두세요.

#### (1) 워크플로우 시스템 설계 문서 (1-2 페이지)

다음 섹션으로 작성해 주세요:

- **Scope:** 무엇을 만들 것인가
- **Architecture:** 컴포넌트 구성과 DAG 표현·실행 방식
- **Failure modes:** 노드의 로그·메트릭 수집, 실패 전파·재시도 정책
- **Trade-offs vs Argo:** Argo Workflows 등 기존 솔루션과의 차별점·트레이드오프
- **What I intentionally skipped:** 의도적으로 생략한 부분과 그 이유

#### (2) 워크플로우 최소 PoC

- 위 설계가 실현 가능함을 증명할 정도
- 3-4개 노드를 가진 간단한 DAG가 순차 실행되며 로그를 남기는 수준
- 본격적인 실행 엔진을 만들 필요는 없습니다. K8s 배포는 선택. 로컬에서 잘 동작하는 작고 명확한 demo를 권장합니다.

#### (3) 실제 학습 잡 로그 분석 AI 에이전트 (핵심 산출물)

- 학습 잡 로그·메트릭을 입력받아 실패 원인을 분석하고 액션을 제안
- Mock 데이터가 아니라 실제 학습 잡 로그를 사용하세요 (제공 자료 섹션 참고)
- Agent 시스템 디자인은 본인이 결정: 도구 선택·context 관리·종료 조건·retry·human approval·실패 처리
- 권장: 진단 결과를 structured format(JSON/schema)으로 출력, 불확실성·추가 확인 액션 구분
- 실행 demo: 라이브 URL 또는 로컬 demo 둘 다 허용. 평가자가 README 따라 10분 이내 재현 가능해야 합니다

#### (4) 회고 로그 (README, 1페이지 이내)

- 사용한 AI 도구
- AI 사용 판단 (AI에 맡긴 것 vs 직접 판단한 것) — 구체 사례 2-3개
- AI 출력 중 버린 것 1개 (구체 예시 + 이유)
- 실제 투입 시간 총합

### 3.2 선택 산출물 (가산점)

- Cache reuse / 재실행 전략 / human approval 게이트
- 진단 결과의 confidence threshold
- DAG 시각화: 워크플로우의 노드·엣지·실행 상태를 시각적으로 표현. 본인이 가장 빠르게 만들 수 있는 도구로 (특정 프레임워크 강제 없음)
- 진단 결과 대시보드 (단순한 형태도 충분)
